## Reproduction, changes and retesting

- QC-001: run tests/run.sh against original connection code. DB-003 reports foreign_keys=0; DB-004 accepts nonexistent member. Baseline log has 12 passes/10 failures, including downstream fixture contamination after unsafe delete. Those 10 failures are not 10 independent defects. Correction enables FK and 5000ms busy timeout on every SQLite connection before transactions; closes connection if configuration fails. All corresponding final regressions pass. No schema or stored data rewritten. Enabling constraints may expose pre-existing bad production data; that requires a read-only integrity audit before rollout, not automatic deletion.
- QC-002: PAY-007 creates member-2 payment referencing subscription 1 owned by member 1. Expanded baseline accepts it. Correction rejects nonexistent or wrong-owner subscription before write, for save and update. PAY-007/008 verify rejection and retained original attribution. This protects the tested sequential API path; concurrent ownership reassignment still needs a database-level composite constraint/transaction design and concurrency tests.
- QC-003: direct update(null) previously dereferenced null. PAY-009 now confirms validation rejection. Existing valid payment CRUD still passes.
- QC-004: on newly migrated disposable database, insert members with distinct codes but same phone. Both rows persist; test cleans its own synthetic extra row. Fix requires a new migration version, normalization/blank-phone policy, existing-duplicate detection and tested server-engine upgrade compatibility. Unregistering/reusing 008 or deleting duplicate customer data would be unsafe; no such change was made.
- QC-005/006: `python3 qa-reports/tests/backup_reproduction.py` reproduces the same filesystem-copy primitive, not the interactive controller buttons. Source links show that primitive is the implementation. WAL source has 1 committed row, copied main DB has 0. Invalid .db copy succeeds and subsequent integrity check fails. A safe correction needs a consistent snapshot API, validation, staged atomic recovery, connection coordination and loss/interruption tests. No live restore was attempted.
- QC-007/008: source review establishes storage and transport defaults, but severity is deployment-dependent. Fix without changing production credentials; adopt credential store and tested TLS provisioning.

## Additional packaged-runtime defect QC-013

**Severity: HIGH. Status: corrected in packaging configuration; Linux runtime verified, Windows verification NOT EXECUTED.**

Location: `.github/workflows/build-windows.yml:111` (jpackage Java options; locate `--add-reads`). Using the configured all-libraries module path resolves SQLite as `org.xerial.sqlitejdbc`. SQLite's SLF4J logger cannot access legacy module `slf4j.api`; `DriverManager` then reports no suitable SQLite driver. A clean JDK/classpath test does not reveal the problem. Original app-image startup failed, and the minimal packaged DriverProbe exposed the underlying IllegalAccessError in evidence/packaged-driver-probe.log.

Small correction adds `--add-reads=org.xerial.sqlitejdbc=slf4j.api` to jpackage launcher configuration. The packaged driver connects successfully with this option; a new Linux app image embeds the option and is smoke-tested separately. SHA-256 confirms its GymFlow.jar matches the final clean build. Windows EXE installation and service loading still need their own acceptance test. Changes to `.github/workflows/build-windows.yml` are QC changes in addition to the two named Java files. No CI workflow or release was triggered.
